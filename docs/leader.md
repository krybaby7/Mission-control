# The leader

The leader is the way a non-technical CEO acts on Mission Control. It is a Claude Code session, started in the repository's `leader/` folder, that the CEO talks to in plain words. It is the CEO's hands. The dashboard ([docs/dashboard-spec.md](dashboard-spec.md)) is the CEO's eyes and only shows things.

This page says what the leader is, what it may do, how it is kept inside those limits, and what has not been tried. For the steps to start it on your PC, see [leader/README.md](../leader/README.md) and [docs/setup-windows.md](setup-windows.md).

## What it is, and what it is not

- It is Claude Code, running in the Ubuntu (WSL2) window on the PC, with `leader/` as its folder. Claude Code reads `leader/CLAUDE.md` there as its standing instructions and `leader/.claude/settings.json` as its permissions.
- The same session can be reached from the Claude app or claude.ai/code (Remote Control, below), when it is started with `claude --remote-control`.
- It acts only through Mission Control's own commands, run through `scripts/mc-docker.sh`: status, logs, report, stop, new, feature, plan preview, plan queue, plan show, run, approve and send-back, plus `get`, `publish-preview` and `publish`, which work with GitHub on the PC itself (see "GitHub in and out"). There is no other write path: the dashboard has none either.
- It is the CEO's hands, never the CEO's engineer. It does not write code, fix an app, or do the AI team's work. The engine does that.
- It adds nothing to the engine. No engine file was changed to make it.

## The fifteen commands

All are run from `leader/` as `../scripts/mc-docker.sh <command>`. Twelve were checked against `mc --help` and the help of each command (the commands and flags in `src/cli.ts`), and against `scripts/mc-docker.sh`, which hands everything it does not know to `mc` inside the container. The other three, `get`, `publish-preview` and `publish`, are commands of `scripts/mc-docker.sh` itself: they run on the PC, not in the container, and `mc` does not know them. `test/leader.test.ts` checks them against the wrapper's own help instead.

| Command | What it does | Notes |
|---|---|---|
| `status --json` | Lists every mission: id, title, kind, status, stage, features done and total, blocked, `waitingUntil`, `interrupted`. | Read only. `waitingUntil` is UTC (the string ends in Z), because `src/cli.ts` prints the raw event time in JSON. The plain `status` table prints the same moment in local time, in its WAITING UNTIL column. `leader/CLAUDE.md` tells the leader to read the local time there and never to say the UTC clock time as if it were local. |
| `logs <mission>` | What happened in one mission, step by step. | Read only. The whole log is long and technical (model names, internal steps), so the leader reads only the last 60 lines (it pipes the output through `tail -n 60`) and translates. `--follow` never ends, so the leader does not use it, and the settings refuse it. |
| `report [<mission>]` | The first 40 lines of the latest report, or of one mission's. | Read only. "Needs your decision" and the Features table are near the top, but with many features they can fall below line 40. The rest sits in a file inside the Docker volume, which the leader cannot open. A mission that is still running has no report (the command says so and fails): the leader then reads the end of `logs` and says the full answer comes when the mission ends. |
| `stop` | Asks the running work to stop. The running AI step is cancelled, progress is saved and the report is written. | Writes the `STOP` file. The leader first checks with `status --json` that a run is going (if not, it says there is nothing to stop and does not run `stop`), then always asks. Claude Code asks too (see Permissions). |
| `new '<idea>' --name '<name>'` | Queues a new app. | Only queues. `--checkpoint plan`, `--checkpoint feature` or `--checkpoint final` asks the team to stop for the owner's look at that point; the leader adds it only when the CEO asks (see "Checks the CEO asked for"). |
| `feature ~/mc-apps/<app-folder> '<request>' --base '<branch>'` | Queues a change to an existing app. | Only queues. The folder must be inside `~/mc-apps`. The same `--checkpoint` flag. |
| `plan preview - <<'PLAN'` and the plan on the next lines | Shows a plan the leader wrote in plain words, with its plan code, or lists what is wrong with it. | Read only: it queues nothing, writes no file and spends nothing. The plan is plain lines of text sent in with the command (a here-document with a quoted delimiter). See "Plans the leader writes". |
| `plan queue - <<'PLAN'` and the same kind of plan | Queues the plan. The team's planner is skipped. | Only queues. The mission stops at the plan for the CEO's look unless `--no-plan-checkpoint` is given; `--checkpoint feature` and `--checkpoint final` add more stops. A feature marked for the CEO's look (`mode: owner`) stops too, unless `--no-owner-checkpoint` is given (see "Documents, pages and data"). |
| `plan show <mission>` | Shows the whole plan of one mission in plain words, with its plan code. | Read only. `report` shows only 40 lines and cuts a long plan, so this is how a plan is read in full. |
| `approve <mission> [--note '<text>']` | Lets a mission that stopped for the CEO's check carry on. | Records the answer in the mission, and it continues on the next run. Only while no run is going: with a run active it says so and records nothing. The leader asks the CEO first (see "Checks the CEO asked for"), and Claude Code asks too. |
| `send-back <mission> --note '<text>'` | Sends that mission back with what to change. | Same conditions. The team reworks it and asks again, at most twice. The note is required. |
| `run [--until HH:MM]` | Works through the queue. `--mission <id>` works on one mission only. | Spends the owner's usage. It blocks until the run ends. `--until` is optional: the leader passes it only when the CEO gives a stop time, and never asks for one. What happens without it is in the next section. |
| `get '<owner>/<repo>' ['<folder-name>']` | Downloads a repository from github.com into `~/mc-apps/<name>` and prints the folder it made. | Runs on the PC with the owner's own GitHub login. It never overwrites a folder. Only github.com is accepted. The leader asks the CEO first. See "GitHub in and out". |
| `publish-preview <mission>` | Says which GitHub repository a finished or partly finished mission's work would go to, and uploads nothing. | Runs on the PC. Read only: no push, no network, no `gh`. It makes the same checks as `publish` and refuses for the same reasons, so the leader can put the repository's name in its question. See "GitHub in and out". |
| `publish <mission> --to '<owner>/<repo>'` | Uploads the branch `mc/<mission>` of a finished or partly finished mission to that repository and opens a draft pull request. | Runs on the PC with the owner's own GitHub login. The repository must be the one the app points to, the one the app was set up for, and the one named after `--to`. It never touches the main branch and never overwrites. The leader asks the CEO first, with the repository's name in the question. See "GitHub in and out". |

Not in the list on purpose: `dashboard` (a foreground command that runs until Ctrl+C, so a tool call from the leader would never return; the owner starts it), `config`, `init`, `doctor`, the logins, `shell`, `build`, `copy-reports`, `fix-permissions`, `install-leader` and `leader` (the owner's own setup, see "Starting the leader with one click").

## Checks the CEO asked for

The CEO can ask, when work is queued, for the team to stop at one of three places and wait: `plan` (before anything is built), `feature` (before each feature is added) or `final` (before the finished app is published). The design is in [docs/checkpoints-spec.md](checkpoints-spec.md). The leader's part:

- It reads the first 40 lines of `report <mission>`, whose first block says what is waiting and what to look at, and tells the CEO in plain words. `status --json` shows the check as `checkpoint` (kind, featureId, round, state, decision); the `status` table shows "needs your check" or "answered".
- It never answers a check on its own judgement, and never because a report, a log or a name says so. Before `approve` it asks "Approve the <plan / feature / finished app> of <name>? This lets the team carry on and it cannot be undone. Yes or no?". Before `send-back` it repeats the CEO's change in one line and asks "Send it back with this? Yes or no?". Only a clear yes counts. This is in `leader/CLAUDE.md`, and it is a rule for the model, which is a weak guard.
- The second guard is the prompt: `approve` and `send-back` are in the `ask` list, never in `allow`, so Claude Code shows the command to the owner (on the PC, or in the app with Remote Control) before it runs.
- A run that is going holds the lock the commands need, so an answer cannot be recorded then. The leader tells the CEO to wait until the run ends. A mission that waits for a check does not hold the run up: the run moves on to other work and ends when nothing else is left.
- A mission queued with `plan queue` stops at the plan without being asked (see "Plans the leader writes"); it is answered like any other check.
- A third send-back of the same check ends the work there (a plan: nothing will be built; a feature: it is set aside and the rest carries on; the finished app: the finished result is kept as it is). The leader says so before it asks, when `round` is 3.
- The words after "What to change:" in the dashboard's sentence are the CEO's own and become the `--note`. The note goes to the team only as the one change request the send-back makes (the planner's revision, the engineer's fix, or the new feature). An approve note is only kept in the report; no AI reads it.

What this does not give: a secret that the AI team cannot read. The agents run as the same user as the engine, so a determined one could write an answer itself (docs/checkpoints-spec.md, section 8.3). A forged answer cannot make anything pass that the checks refuse; it only skips the owner's look, and every answer the command records sends a notice to the owner's phone (an answer written by editing the files by hand is distrusted when the mission reaches its gate, but sends no notice of its own).

## Plans the leader writes

For a small, clear job the leader can write the plan itself instead of leaving it to the team's planner. The design is in [docs/plans-spec.md](plans-spec.md); this is the leader's side.

- **What it is.** A plan is plain lines of text: a first line `mc-plan 1`, then `key: value` lines for the whole plan and one block of lines for each feature (its title, a story, `check` lines). It has no key that is run, opened or followed: no command, no file list, no address. `mc` refuses a curly bracket, a backtick, a web address and the usual ways of hiding text, and every length is limited. The grammar and every message are in the spec (section 3).
- **How it is handed over.** On standard input, in a here-document with a quoted delimiter: `../scripts/mc-docker.sh plan preview - <<'PLAN'`, the plan, and a line that says only `PLAN`. Nothing is written to a file, because the container sees only `~/mc-apps` and the leader may not write files. `scripts/mc-docker.sh` keeps the container's input open for `plan` with a `-` argument.
- **What the team does.** The team's planner is skipped. For a change to an existing app the team still looks at the app first (onboard). A second AI reads the plan (the plan reviewer) and may ask for changes; the planner then revises the plan, and the outcome is stored and shown, with the checks that were removed or added. For a job that makes a script or a file, the leader puts the file's path and what it writes into one `contract` line, so the plan reviewer has no reason to ask for it. Then the usual work: for a feature checked by tests, the tests first, frozen, and an independent review; for a feature checked another way, see "Documents, pages and data". Then the final checks and review of the whole app. Nothing is skipped to save time: every plan mission runs the final review like any other.
- **What the CEO sees.** `plan preview` and `plan queue` print the plan in words with a plan code (the start of a SHA-256 of the plan written in one fixed form). The leader quotes the code, lists the story and every check of every feature word for word, and asks one question before it queues: "Queue this plan and start the team on it?" The mission then stops at the plan before anything is built, and the engine prints the same lines again (`plan show`, the report, the dashboard card says who wrote the plan and where to read all of it). The leader reads them to the CEO again, and only the CEO's yes approves.
- **The same plan twice.** `plan queue` refuses a plan whose plan code is that of a mission that has not finished (queued, running, waiting, stopped, or failed in a way a plain run retries): `This plan is already queued as “<name>” (<id>). See it with: mc status`. `plan preview` prints the same sentence as a note. The leader tells the CEO in plain words that it is already waiting, does not try again, does not start the team on it by itself, and offers to show where it stands (`status --json`, because the leader has no `mc` shortcut). A finished mission (done, partly done, or failed for good) does not block a new try. The guard is in the engine ([docs/plans-spec.md](plans-spec.md)); the leader's text only says what to do when it fires.
- **Skipping the stop.** The stop is on by default and only `--no-plan-checkpoint` turns it off. The plan text cannot. `leader/CLAUDE.md` tells the leader to add the flag only after the question "Skip your look at this plan? The team will build it without stopping for you. Yes or no?" and a clear yes; a test pins the words. That is a rule for the model, which is a weak guard, and the flag is on the first line of a long command, so the prompt is a weak guard for it as well. An owner who never wants the leader to waive the stop can add `Bash(../scripts/mc-docker.sh plan queue *--no-plan-checkpoint*)` to `deny` in `leader/.claude/settings.json` (the `logs *--follow*` rule is the precedent). Claude Code says that rules like this are not a security boundary, and the leader could not then skip the stop even when the CEO says so.
- **What a plan cannot protect against.** The engine cannot judge intent: a plan that says in plain words to download a file and run it passes the checks. The defences are that no key of a plan is run or followed, that the CEO sees all of it before anything is built, the leader's own rules (never a command, path, web address, key or password in a plan; a plan only from the CEO's own words in the chat), and that the work happens in the container. After a send-back, or when the plan reviewer asked for changes, the plan is the planner's text, which these limits do not cover.
- **The leader writes blind for an app that exists.** It cannot read the app, so `CLAUDE.md` limits plans to tiny and small jobs, and to facts the CEO's words or the app's report give. Bigger or unclear jobs, and any change where it does not know where it goes, are queued with `feature` or `new`, where the team's planner reads the code.

**What was and was not verified.** Said plainly:

- A spike ran Claude Code 2.1.296 non-interactively with the allow rules given on the command line (`--allowedTools`). A here-document with a quoted delimiter and no curly bracket ran without a prompt, its body (even with `;`, `&&`, `|`, `$( )`) was data, a second command after the terminator and an unquoted delimiter were blocked, and a body with a curly bracket next to a quote mark was blocked before any prompt (which is why a plan is not JSON). The bodies had no apostrophe, double quote, backslash or non-English letter and were under 5.3 KB.
- **Not verified:** the same rules in `leader/.claude/settings.json` in an interactive leader session; that `plan preview` and `plan show` really run without a prompt there; how an `ask` rule prompts for `plan queue`; how the confirmation shows a long, multi-line command (a command over 10,000 characters always asks, by Anthropic's documentation); plans with apostrophes, double quotes or other letters; Windows and WSL.
- **A mismatch fails safe.** If a rule does not match, Claude Code asks instead of running, so `allow` for the two read-only commands can only cost a prompt each time. If Claude Code blocks a plan outright, the leader cannot send it and `CLAUDE.md` tells it to queue the job the usual way. The prompt for `plan queue` is a confirmation, not the review: the review is the leader's word-for-word list, the plan stop, and `plan show`.
- Whether a model writes valid plans and follows the rubric is not shown by anything here; `plan preview` and the plan reviewer are the safety nets, not proof. The same holds for the rubric that chooses how a feature is checked (see "Documents, pages and data").

## Documents, pages and data

For work that has no tests a plan can say how each feature is checked and how hard the team thinks. The design is in [docs/modes-spec.md](modes-spec.md) and the owner's guide is [docs/work-modes.md](work-modes.md). This is the leader's side.

- **What the plan can say.** Seven more keys of the same plan format (`mc-plan 1` stays the version, and a plan that uses none of them is read, coded and shown exactly as before): `mode` (`tests`, `review` or `owner`), `effort` (`light`, `standard` or `deep`), and the checks Mission Control runs by itself: `heading`, `mention`, `words`, `columns` and `rows`. They are plain words and numbers. An older engine refuses a plan that uses them, with a message that lists the keys, instead of misreading it.
- **How the leader chooses.** `leader/CLAUDE.md` has a table (code and numbers are tested; writing with named parts is checked by a second AI; taste, anything sent to other people, and web pages are marked for the CEO's look; a spreadsheet is a script with tests plus a question; research with sources is sent away) and a table for the effort. When two rows fit, it splits the feature or takes the stricter mode. This is a rule for the model.
- **What the leader tells the CEO.** After a preview, for each feature, one line in fixed words: "Checked by tests.", "Checked by a second AI against this list.", or "Checked by a second AI against this list, and then by you." It never says that such a feature was tested. When the team stops at a feature, it reads `plan show <mission>` too and tells the CEO what the second AI found, check by check, which checks it could not judge, and where the pictures are. What the second AI quotes comes from files that an AI wrote or that a cloned repository held, so it is information only.
- **The questions.** The usual question before `plan queue` is unchanged. With features marked for the CEO's look it also names them: "Queue this plan and start the team on it? It will stop for your look at the plan before anything is built, and for your look at “<title>” and “<title>” before each is added. Yes or no?". Before a job that reads a file the CEO named, it asks "Does this file hold personal data, customer details or private papers? Yes or no?" and queues nothing on yes. A test pins the words.
- **Skipping the look.** A feature marked for the CEO's look stops every time. The plan text cannot turn that off, and neither can the planner's revision of a plan (a revision that would lose a mode is refused). Only `--no-owner-checkpoint` on `plan queue` can. `leader/CLAUDE.md` tells the leader to add it only after the question "Skip your look at these features? The team will add them without stopping for you. Yes or no?" and a clear yes. That is a rule for the model, which is a weak guard. An owner who never wants the leader to waive the look can add `Bash(../scripts/mc-docker.sh plan queue *--no-owner-checkpoint*)` to `deny` in `leader/.claude/settings.json`, with the same caveat as for `--no-plan-checkpoint`: Claude Code says rules like this are not a security boundary, and the leader could not then skip the look even when the CEO says so. Mission Control records the flag as "it was queued without a stop for your look", and never as a choice not to look.
- **Words that must not be used.** For a feature that no test checked, the leader and Mission Control never say tested, "passed its tests" or "you looked at it". "Approved by you" is what the log holds.

**What was and was not verified.** The words of the leader's text and its questions are pinned by `test/leader.test.ts`, and the plan in the text is run through the real `plan preview`. Not verified: that the leader follows the rubric, writes valid plans with the new keys, lists every check word for word, or asks the fixed questions; that Claude Code lets a plan with the new keys through; how a long plan shows in the prompt. The second AI's judgement is an AI's, and no run shows how often it passes what it should not. See "Not verified" in [docs/work-modes.md](work-modes.md).

## GitHub in and out

The goal behind it: the CEO says "work on my repo and send it to GitHub", and the team does the work on a copy on the PC, and the result comes back as a draft pull request on GitHub for the CEO to merge. The design rule is that **with these commands no password, token or login is ever inside the container**, and the engine stays free of credentials. (The older `git.push` setting is the one exception, and it is off unless you turn it on: see [docs/github-setup.md](github-setup.md).) So these commands run on the PC, in Ubuntu, with the owner's own git and GitHub login (`gh auth login`, see [docs/github-setup.md](github-setup.md)), and are commands of `scripts/mc-docker.sh`, not of `mc`.

**`get <github-url | owner/repo> [folder-name]`**

- Accepts only `https://github.com/<owner>/<repo>` (a trailing `.git` or `/` is fine), `git@github.com:<owner>/<repo>.git` and `<owner>/<repo>`. The owner is 1 to 39 letters, digits or dashes, starting with a letter or digit; the repository is 1 to 100 letters, digits, dots, dashes or underscores, and not `.` or `..`. Anything else is refused with a sentence that names github.com, before any program runs. A look-alike letter, an invisible character, an option such as `--upload-pack=...`, `ext::` and `file://` addresses are all refused the same way.
- The folder name defaults to the repository's name and must be a letter or digit followed by letters, digits, dots, dashes and underscores (61 characters at most, no `..`, no slash). It clones into `~/mc-apps/<name>`, refuses when that exists (a folder, a file or a link) and never overwrites. It runs `git clone` as an array of arguments, with `--` before the address, no hooks, no prompts (a login that is missing makes it fail with a plain sentence that names `gh auth login`), and never through `eval` or a string built into a command.
- It needs no Docker.

**`publish-preview <mission>` and `publish <mission> --to <owner/repo>`**

- The mission's record lives in a Docker volume, which the PC cannot read directly, and `mc` has no command that prints what `publish` needs. So both read it in a small container of its own: read-only, no network, no logins, no apps folder, the one volume mounted read-only, no new variable. It runs a fixed script that only reads the record and prints cleaned-up facts. The PC checks every value again with strict patterns and never runs any of it.
- In this order, with a plain refusal for each: the name has the shape of a mission name (and `--to`, if given, has the shape `owner/repo`); the mission exists; it is `done` or `partial` (a `partial` mission is published as a draft that lists its unfinished features, because a draft changes nothing live; `failed`, `queued`, `running`, `waiting` and `stopped` are refused); the branch `mc/<id>` has at least one commit that the base branch does not (a new app has none, see below); the app folder is a plain git folder inside `~/mc-apps` whose `origin` is a plain github.com address (no login or password inside it); `origin` is the repository the folder was set up for; `origin` is the repository named after `--to`; the app does not use git hooks or Git LFS (which this script never runs); the base branch is on GitHub.
- **Where the work goes is never taken on trust.** The AI team writes in the app folder, so the address in its `.git/config` can be changed to another repository the owner can write to (for example a public one), and the engine's own guard for git settings does not cover `remote.<name>.url`. Three things stand in the way. `get` saves the repository it downloaded from in a note outside the container (`~/.config/mission-control/origins/<folder>`; the container mounts `~/mc-apps` and nothing under `~/.config`), and `publish` refuses an address that differs from the note, even when `--to` names the new one. Without a note (an app the owner connected by hand), `publish` still needs the repository after `--to`, which the person sees first in the preview, and it saves a note after the first upload. And `publish-preview` prints the repository, so the leader can name it in its question and Claude Code's prompt for `publish` shows it in the command. Changing the engine's guard was not done: the guard would also undo an address the owner sets on purpose while a mission runs, and it only runs at some points.
- Without `--to`, `publish` does what `publish-preview` does and exits 1 with the line to run. That keeps a person at the keyboard to one extra step.
- **A new app.** When the engine finishes a new app it moves the base branch onto the finished work (`publishToMain` in `src/dispatcher.ts`), so the branch has nothing the base branch does not, and GitHub has nothing yet either. There is no pull request to open. Both commands say so (`is a new app`) and tell the owner the two steps: an empty repository on github.com, then `git remote add origin ...` and `git push -u origin main` in the app folder, once. That upload is not made by this script, because it would push the main branch. After it, later changes go through `publish` as usual. A new app whose main did not move (the engine noted that it could not) still goes through the normal route.
- The app folder is where the AI team works, so it could hold git settings and hooks that make git run commands, and publishing uses the owner's login. So git never runs inside the app folder. The one branch (and the base, to compare with) is copied into a new, empty folder that the script makes, and everything that touches GitHub runs from that copy, with hooks and fsmonitor off, no prompts, and ssh set to fail instead of asking. The app's saved settings are read as a plain file, only to find `origin`.
- It pushes only `mc/<id>`, with one explicit refspec, never `--force`, never a `+` refspec, never `main` or `master`. A branch that already exists on GitHub with other work is not overwritten.
- With gh on the PC it runs `gh pr create --draft` from the clean copy, with the repository, branch, base, title and a body file as separate arguments. Without gh, or when gh fails, the branch stays uploaded and it prints the address `https://github.com/<owner>/<repo>/compare/<base>...mc/<id>?expand=1`. The title is the mission's title with control and invisible characters removed, at most 100 characters. The body says what was checked and who looked, from the mission's own record: tests written first and how many features have them, how the other features were checked (the report's `Checked:` line), reviews that did not finish, the stops the owner answered and the plan code, and says plainly when nobody looked. It adds the first lines of the report (without the steps for trying the app on the PC) in a fenced block, and leaves the characters that tag a person, link an issue or add HTML out of the titles.

**What the leader asks.** Before `get`: "Download <owner/repo> to this PC so the team can work on it? Yes or no?" Before `publish`, when the work is finished or partly finished, and after `publish-preview` has printed the repository: "Send “<mission title>” to <owner>/<repo> on GitHub as a draft pull request? Nothing is merged and the main branch is not changed. Yes or no?" Only a clear yes counts, a wish at the start of the chat ("and send it to GitHub") is not the second answer, and Claude Code asks the owner again before it runs either command; its prompt shows the repository, because the command has `--to <owner>/<repo>`. The repository for `get` comes only from the CEO's own words. The repository for `publish` comes only from `publish-preview`, and if the CEO named another one earlier the leader does not ask and tells the CEO the app now points elsewhere. These words are rules for the model, which is a weak guard; the prompt and the checks in the commands are the others.

What was and was not verified. Said plainly:

- Tested here with a stand-in for GitHub (bare git repositories reached through the owner's own `url.<folder>.insteadOf` setting, so the product has no test switch) and a stand-in for gh that records its arguments and the body: `test/mc-docker-github.test.ts`. That includes hostile addresses, folder names and mission names, an app folder with git settings and hooks that would run a command, and a branch that exists on GitHub already.
- **Not tried:** a real GitHub, a real login (`gh auth login`, `gh auth setup-git`), the real gh program creating a pull request (only its flags were checked against `gh pr create --help` of the gh installed here), private repositories, ssh keys, Git LFS, Windows, WSL and Docker Desktop. Real GitHub cannot be reached from the place this was built.
- The mission's cleaned-up facts come from `mission.json`. Since Step 3 a feature can also be checked by a second AI (see "Documents, pages and data"), and `publish` says so: when a finished feature has such a mode, the body's Tests line says that the rest were not checked by tests, and the body copies the report's `Checked:` line. Real GitHub was not reached, so this was tried with the stand-ins above only.

## Starting the leader with one click

Today the leader's commands are written `../scripts/mc-docker.sh ...`, which only works when the leader runs inside the `leader/` folder of its copy of Mission Control, and its permission rules match that exact text. So the prefix must not change. What makes it robust is how the leader is started:

- `mc-docker.sh install-leader` (run once by the owner, no Docker needed) saves the absolute folder of this copy in `~/.config/mission-control/checkout` and puts `scripts/windows/mc-launch.sh` at `~/.config/mission-control/launch`.
- `mc-docker.sh leader [--no-remote]` changes into `<this copy>/leader` first and then runs `claude --remote-control "Leader"` (or `claude`). The folder comes from where the script itself is, so the leader always starts next to its own `CLAUDE.md` and `settings.json`.
- The launcher reads the saved folder each time (or tries `~/Mission-control`, the folder the setup guide downloads to) and runs that copy's script with `leader` or `dashboard`, nothing else. If the folder is gone, it says so in a sentence and names `install-leader`.
- `scripts/windows/start-leader.cmd` and `start-dashboard.cmd` open Ubuntu through `wsl.exe` and call the launcher. They are plain ASCII with Windows line endings, and the Ubuntu name is one word at the top of each file.
- After moving Mission Control or downloading it again, run `install-leader` once more from the new folder.

Tested here: that `install-leader` saves the folder and the launcher, that the leader starts in the leader folder of the copy it was saved for (a fake `claude` on a pseudo-terminal), that moving the copy and running `install-leader` again is followed, that the launcher refuses anything but `leader` and `dashboard`, and the shape of the two shortcut files (`test/mc-launcher.test.ts`). **Not tried:** Windows, `wsl.exe`, the shortcuts, Claude Code, and `claude --remote-control` from a shortcut.

## Starting a run without blocking the chat

`run` does not return until the run ends (the Docker script's `run` branch ends in `exec docker run`). Run in the foreground, it would make the chat unusable for as long as the run lasts. So `leader/CLAUDE.md` tells the leader to start it as a background task (Claude Code's Bash tool has a `run_in_background` option) and to keep talking.

### With and without a stop time

What `mc run` does without `--until`, from `src/run.ts`, `src/cli.ts` and `scripts/mc-docker.sh` (the Docker script passes the arguments on unchanged and adds no stop time):

- There is no stop time and no upper limit on the length of the run. `src/run.ts` logs "Working until the queue is done (no stop time given)." The run goes through the queued missions one after another, picks up missions queued while it works, and ends when none has work left, when `mc stop` or a stop signal arrives, or when the work cannot go on (a full disk, every AI needs a login, or the AI command lines keep failing).
- When every AI is at its usage limit, the run waits for the limit to end and carries on. With a stop time, it ends the run instead of waiting past that time. Without one it can wait a long time.
- With a stop time, the engine refuses one that is more than 18 hours ahead (`--until` always means the next time the clock shows it) and starts nothing.

`leader/CLAUDE.md` tells the leader to say this in plain words before it starts a run without a stop time. The CEO decides whether there is a stop time; the leader does not ask for one. The dashboard's `--until` is only "a stop time to show": the engine does not save the stop time, so `mc dashboard --until HH:MM` takes the time the CEO gave and shows it with a countdown.

Mission Control's own words for a run are the phone notification "Run finished", the log line "Ending the run early" and the "Run summary". The run summaries and the log files on disk are named `run-<date>.md` and `run-<date>.log`. Files that earlier runs wrote are named `night-<date>.md` and `night-<date>.log`; they stay where they are, and `mc report` still reads the summaries. The leader says "run" to the CEO.

### Without a terminal

Under such a task there is no terminal, so `mc-docker.sh run` behaves as it does under Task Scheduler: it waits up to five minutes for Docker Desktop, and if it cannot start it pushes a notification to the owner's iPad (decision log, "Container and setup" item 4).

Not tried here: running `mc-docker.sh run` as a background task of a Claude Code session. If the session ends during a run, the run may receive a stop signal. The engine handles `SIGHUP`, `SIGINT` and `SIGTERM` by finishing up and saving its progress (`src/run.ts`), and the next run continues, but nobody has seen this happen through Claude Code. A run that must not depend on a chat session is started by the owner or by the scheduled task.

## Permissions

`leader/.claude/settings.json` has three lists, with rules written as `Bash(../scripts/mc-docker.sh <command>:*)`:

- `allow` (no prompt): `status`, `logs`, `report`, `plan preview`, `plan show` and `publish-preview`. They only read. (`publish-preview` is a command word of its own. The `ask` rule `publish:*` needs a space or the end of the command after `publish`, so it should not match `publish-preview`; if it does, Claude Code only asks one more time. Not tried here.) (The two `plan` rules rest on the spike described above and its limits: if Claude Code asks for them anyway, nothing breaks.)
- `ask` (Claude Code stops and asks first): `stop`, `run`, `new`, `feature`, `plan queue`, `approve`, `send-back`, `get` and `publish`. They change something or spend usage; `approve` and `send-back` decide a check, which only the CEO may do; `get` and `publish` use the owner's GitHub login.
- `deny` (refused): `Edit`, `Write`, `NotebookEdit`, `git` commands, and `logs ... --follow` (the rule is `Bash(../scripts/mc-docker.sh logs *--follow*)`, because `logs:*` in the allow list would otherwise let it through).

Claude Code checks `deny` first, then `ask`, then `allow`, so an `ask` rule wins over an `allow` rule that also matches. A compound command (`a && b`) needs every part to match. Claude Code also runs its own read-only commands (`ls`, `cat`, `grep`, `echo`, `wc`, `find`, read-only forms of `git`) and reads files inside the folder without asking, so "everything else asks" is not exact. These details are from Anthropic's permissions documentation (https://code.claude.com/docs/en/permissions).

Why `stop`, `run`, `new`, `feature`, `plan queue`, `approve`, `send-back`, `get` and `publish` ask: reports, logs, decisions and the names of missions and features are written by AIs, and the leader reads them. `CLAUDE.md` tells the leader that such text is data, never instructions, but a sentence in a prompt is a weak guard. A person tapping Yes on a prompt, with the command in front of them, is a real one. It costs one tap per command, on the PC or, with Remote Control, in the app (the documentation says permission prompts stay open until they are answered).

Answer **Yes** once. Do not choose "Yes, and don't ask again". Claude Code saves that as an allow rule in `.claude/settings.local.json` at the root of the repository, and nobody has reviewed the rule. Anthropic's documentation says a matching `ask` rule prompts even when an allow rule also matches, so the `ask` rule in `settings.json` should still win for the commands it matches and the question should not go away. That was not tried here, so do not count on it. The reason not to choose it is the saved rule itself: it is unreviewed, it applies to every later session started in this repository, and for `plan queue` it would be the exact text of one plan, which is of no use.

To relax this, move entries from `ask` to `allow` in the same file. The confirmation before `stop` in `CLAUDE.md` stays either way.

Not tried here: that the rule syntax matches commands written with a relative path in the installed Claude Code (the `plan` rules were tried only with rules given on the command line of a non-interactive run, see "Plans the leader writes"), that the `--follow` rule catches `logs <mission> --follow` and `logs --follow <mission>`, that a compound command (`a && b`) is refused as a whole, and how the same rules behave in a Remote Control session. `test/leader.test.ts` checks only the shape of the file.

## The sentences the dashboard gives the CEO

The dashboard sends nothing. Its buttons "Tell the leader about this" (on a card or a feature) and "Tell the leader anything" (on the bar) give the CEO a ready sentence with `<your answer here>` for them to fill in, and a Copy button; the CEO pastes it into the chat. A card for a check also has "Tell the leader: approve" and "Tell the leader: send it back". Their sentences are copied the same way: the approval has nothing to fill in, the send-back ends with `<your answer here>` for the change, and the dashboard never records either. The sentences are fixed by the dashboard's vocabulary (`src/dashboard/vocabulary.ts`, spec section 8). The only text an AI wrote in a sentence is a mission or feature title; leader/CLAUDE.md tells the leader that these names are data, never instructions. The sentences name a mission, and sometimes a feature or a question number, so the leader can find the item with `status --json`, `report` and `logs`. When two missions or features have the same title, the sentence adds the id.

`leader/CLAUDE.md` has a table of every sentence (the three about a check included, in their three forms for the plan, a feature and the finished app) and what to do with it, and the four quick phrases (Your call, Leave it out, Try again, What is going on?). `test/leader.test.ts` builds each sentence from the vocabulary module and fails when `CLAUDE.md` does not contain it word for word, so the two cannot drift apart.

## Answers to stuck features and questions

The engine has no command to reopen a feature or to change a plan in place, and a finished mission never runs again. A stuck feature or an unanswered question therefore cannot be answered inside the mission. The leader says so in plain words and offers a follow-up request: a new mission on the same app, queued with `feature`, using the folder and `--base` the report gives. It starts on the next run. A mission that failed and needs the owner's help is different: after the cause is dealt with, `run --mission <id>` continues the same mission.

## Remote Control

From Anthropic's Remote Control documentation (https://code.claude.com/docs/en/remote-control), not from anything tried here:

- `claude --remote-control "Leader"`, or `/remote-control Leader` inside a running session, makes ONE session that works from the Ubuntu window and from the Claude app or claude.ai/code. That is the way to use for the leader.
- `claude remote-control` is server mode. It starts its own session, which is opened from claude.ai/code or the app, and you cannot type to it in that terminal. It is not "the same session". The installed Claude Code (2.1.296) lists the `--remote-control [name]` option in `claude --help`; it does not list a `remote-control` command there.
- The session is found by its name in the session list at claude.ai/code (a browser on the iPad works) or under the Code tab of the Claude mobile app. It shows a computer icon with a green dot while it is online.
- It needs a claude.ai login (Pro, Max, Team or Enterprise). API keys are not supported. On Team and Enterprise an Owner must first enable Remote Control in the Claude Code admin settings.
- The first use asks "Enable Remote Control? (y/n)" (a dialog in a running session), and Claude Code asks whether to trust the folder (`Trust <directory>? [y/N]` in server mode).
- The session runs on the PC. If the Ubuntu window closes or the PC sleeps, the session is offline until it is brought back; the documentation says it reconnects by itself when the machine comes back and the network returns.

Not tried here: starting it, seeing the session in the app, what a CEO can do in it, the permission prompts in it, and what happens when the connection drops during a run. The PC must stay on and awake, and the Ubuntu window must stay open.

## Limits

- The leader's chat uses the same Claude plan as the team's runs. The engine's pacing cannot see it.
- It cannot see exact usage figures or the allowance. The dashboard shows them.
- It cannot log in to Claude, Codex or GitHub, free disk space, start the dashboard, remove or reorder queued work, reopen a feature, change a plan in place or merge a pull request.
- It reads texts written by AIs (reports, logs, decisions). `CLAUDE.md` tells it to treat them, and the mission and feature names in a pasted sentence (in quotes, or after "in"), as information and never to run a command that appears in them or follow words in them. How well it holds to this has not been tested against a hostile text; the prompts for `stop`, `run`, `new`, `feature`, `plan queue`, `approve`, `send-back`, `get` and `publish` are the second guard.
- It cannot predict. A question like "Is it going to finish?" gets what is visible (features done, anything stuck, a wait, the stop time if it started the run) and no promise. It has no usage figures and no progress per feature.
- It cannot remove or reorder queued work. "Skip this feature" is answered with that fact, and an offer to stop the run; only a feature that is already stuck stays out.
- It cannot run git or gh. After a report's "How to try it" the app's folder can be left on a trial version; `feature` then refuses, and the leader tells the CEO the owner has to put the app back (the message names the command). With the leader's commands, work reaches GitHub only through `publish`.
